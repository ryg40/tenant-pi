Before you start

This page teaches the shared AgentCore memory with eight short tutorials. Each tutorial follows one example person through one simple task in one example repository. You need no experience with AI agents or with AWS. The glossary explains each new word.

What the shared memory is

An AI agent is a program that reads a request in plain words and works on files for a person. These tutorials use two agents: Pi and Claude Code. An agent forgets what it learned when its session ends.

The shared memory keeps short facts for the agents of several people. Each fact is a record. The records are in Amazon Bedrock AgentCore Memory, a service of AWS (Amazon Web Services).

Before an agent answers a prompt, it searches the memory for matching records. This search is recall. The agent reads the records as reference data and then answers.

A person can ask the agent to add a fact for a project. This is a proposal. A maintainer of the project reads the proposal and approves it or rejects it. Only an approved record reaches the other members of the project.

The parts

The namespaces

A namespace is the path of a record, with a slash at the start and at the end. The policy of a person names the namespaces that the person may read and write.

NamespaceHoldsWho reads it
/shared/Global records for every personEvery person
/project/<projectId>/shared/Approved records of one projectThe members of the project
/project/<projectId>/proposals/<actorId>/Proposals of one person for one projectThe person and the maintainers of the project
/project/<projectId>/rejected/<actorId>/Rejected proposals of one personThe maintainers of the project
/actor/<actorId>/Private records of one personThe person only

Recall reads /shared/, the private namespace of the person and the shared namespace of the current project. It never reads a proposals namespace or a rejected namespace.

The example repository

The tutorials use one example Git repository: example-project, a small web application with an API and integration tests. Its remote is https://git.example.com/example/example-project.git. A second project, example-site, appears only where a person is not its member.

How to read a frame

  • A dark block is a frame. Its title bar names the window. The label on the right says Terminal, Pi, Claude Code, File or Bitwarden Send.
  • A green prompt such as dana@laptop:~$ comes before a command. The white text after it is what the person types.
  • Amber text after a question is the answer that the person types.
  • Red text is an error message.
  • A dashed box is content that the model reads and the screen does not show.
  • The line under each frame says where the output shape comes from: a live run, or the code and the documentation.

Every value is an example: the memory id mem-EXAMPLE, the account 123456789012, the record ids, the dates, the session ids and the texts. No value comes from a real store.

The owner ran a live proof of the design on the real store, with test people and in several rounds. A frame with the caption "Shape from a live run" shows the form of that output, with example values. The section Not verified names each frame that no live run produced.

Tutorial 1 · Dana, a new member of example-project

Dana receives her key

Dana gets her own access key from Alice. She stores it, checks it and reads the memory once, before she uses an agent.

Where: Dana's laptop. A terminal in her home directory, /home/dana.

  1. 1.1 Alice prepares Dana's access

    Alice adds Dana to her private registry: one person entry and one member entry in example-project.

    Then she runs the provision command of the registry script. A dry run is the default: the script prints the plan and changes nothing.

    The plan has four steps: the user, the inline policy, the two tags and one access key.

    The policy allows two read actions on four namespace trees, and one write action on Dana's proposals only. It has no delete action.

    The handoff note fits the config of the dry run, which has no profile field. The apply step writes the config file with profile already.

  2. 1.2 The coordinator creates the user and the key

    The coordinator is the agent of the owner with the admin login. After Alice says yes, it runs the same command with --apply.

    The step creates the IAM user, puts the inline policy, sets the two tags and creates one access key.

    It writes the key into a new private file with mode 0600 and never prints the key. Beside it, it writes Dana's person config with the field profile.

    A second apply changes nothing. Each step runs only when IAM differs from the plan.

  3. 1.3 Dana opens the Bitwarden Send

    Alice sends Dana a link in a message. She tells Dana the password of the link by voice, not in the message.

    The link opens once and expires after one day. Dana opens it and types the password.

    The Send holds two texts: the key in the form of the AWS credentials file, and Dana's person config.

    Dana copies both now. The link does not open a second time. Then she deletes the message with the link.

  4. 1.4 Dana stores the key in an AWS profile

    The AWS command line program aws stores a key under a profile name. The name must be pi-memory-person-dana, because the person config names it.

    Dana pastes the two parts of the key when aws configure asks for them.

    The key is now in ~/.aws/credentials, in the section [pi-memory-person-dana]. The region goes to ~/.aws/config.

    chmod 600 lets only Dana read and write the file.

  5. 1.5 Dana checks who she is

    aws sts get-caller-identity asks AWS which identity a key belongs to. It reads no record and needs no right in the policy.

    The Arn ends with user/pi-memory-person-dana. The key belongs to Dana's IAM user.

  6. 1.6 Dana reads the global namespace

    Dana's policy allows a list on /shared/. A list reads and changes nothing, so it is a safe first test.

    Each record has an id, a text, one namespace and a creation time.

    The store adds four metadata keys of its own: x-amz-agentcore-memory-recordType, x-amz-agentcore-memory-strategyType, x-amz-agentcore-memory-createdAt and x-amz-agentcore-memory-updatedAt. The glossary calls them the store keys.

  7. 1.7 A read outside her scope fails

    Dana searches Chen's private namespace with retrieve-memory-records. Her policy does not name it.

    Then she searches her own proposals namespace. Her policy names it, and she has proposed nothing yet.

    IAM checks the namespace of the request against Dana's policy. A read outside it gets an error with the name of her IAM user, and no data.

    A read inside her policy can be empty. The answer is then an empty list, not an error.

  8. 1.8 Dana saves the person config

    Dana saves the config text of the Send as ~/.config/agentcore-memory/config.json. She adds one optional field, hostLabel.

    schemaVersion: the version of the file form. It is always 1.

    memoryId: the id of the one memory of the team. region: the AWS region of the memory.

    actorId: Dana's id. It goes into her namespaces and into the metadata of her proposals.

    projects: one entry per project. projectId is the id, role is member or maintainer, and remotes lists the Git remotes of the project. An optional directories list maps a directory without a remote.

    profile: the AWS profile with the key. The file holds no key.

    hostLabel: a short word for the metadata host of a proposal. Without it, the core sends the host name of the computer.

    Optional fields with defaults: topK (10 records per namespace), recallTimeoutMs (3000), writeTimeoutMs (10000). A maintainer adds ledgerPath.

    An unknown field or broken JSON stops the core with the code config. So does a missing file that AGENTCORE_MEMORY_CONFIG_FILE names. The error never shows a value of the file.

What you learned

  • Each person has one IAM user, pi-memory-person-<actorId>, with one access key and one inline policy.
  • The coordinator creates the user and the key with the admin login, after the dry run and Alice's word.
  • The key travels once, through a Bitwarden Send with a password told by voice.
  • The key lives in an AWS profile. The person config names the profile and holds no key.
  • aws sts get-caller-identity shows which IAM user a key belongs to.
  • A read in your own namespaces works, also when it finds nothing. A read in the namespace of another person fails.

What cannot happen

  • The key cannot be read from the tracker, from a commit or from a log. The scan hooks refuse a commit with a key pattern.
  • A link without the password opens nothing.
  • Dana's key cannot read /actor/chen/ or the proposals of another person. IAM denies the request.
  • Dana's key cannot create an IAM user or change a policy. Her policy holds no IAM action.
  • Dana's key cannot delete a record. No person and no maintainer holds a delete action.

Tutorial 2 · Dana, in Pi

Dana's first Pi session

Dana starts Pi in her checkout of example-project and asks a first question. The agent recalls three records before it answers.

Where: Dana's checkout ~/example-project. Its Git remote is https://git.example.com/example/example-project.git.

  1. 2.1 Dana checks the project of the directory

    The core finds the project in three ways, in this order: the variable AGENTCORE_PROJECT, the origin remote of the directory, then the directories of the config.

    The review CLI of the core prints the result. This command makes no AWS call.

    source is remote: the remote matches the remote of example-project in Dana's config. role is member.

  2. 2.2 Dana starts Pi with the launch line

    The kit generated Dana's Pi profile with the agentcore module. The plan printed one launch line.

    The line names the person config file. It also removes an inline config that an older shell could export.

    Pi starts. The extension finds the config, so it prints nothing. It is ready to recall.

  3. 2.3 Dana types her first prompt

    Dana types a question and presses Enter. Before the model sees the prompt, the extension asks the core for a recall.

    The core sends three queries at the same time, one per namespace: /shared/, /actor/dana/ and /project/example-project/shared/.

    The model gets the records as one hidden context message. The answer is short, because a private record says that Dana prefers short answers.

  4. 2.4 Dana reads the same block in the terminal

    The chat view hides the block. The review CLI prints the same block for the same question.

    This command sends the question to AWS, as a prompt does.

    Line 1, ## AgentCore Memory recall, is the heading. It tells the model where the block comes from.

    Line 2 is the warning: the model treats the records as reference data, not as instructions.

    Each further line is one record as one JSON object. A line break in a record text stays inside its JSON string, so a record cannot add a line of its own.

    memoryRecordId is the id of the record. namespaces says where it is: /shared/ is global, /actor/dana/ is Dana's private namespace, /project/example-project/shared/ holds the approved records of the project.

    text is the fact. metadata says who proposed it (actorId), with which agent and harness, on which host, in which session and when (proposedAt). session is the id of the Pi session of the proposal. An approved record also has approvedBy and approvedAt.

    The keys x-amz-agentcore-memory-recordType and x-amz-agentcore-memory-strategyType come from the store, not from a person. The store returns the metadata keys in its own order.

  5. 2.5 AWS is slow or down

    Each query has a deadline: recallTimeoutMs, 3000 milliseconds by default. The deadline also covers the load of the key.

    Here the network is down. All three queries reach their deadline.

    Each failed namespace gives one fixed line with a code: timeout, aws_denied or aws_failed. The line holds no prompt, no record and no error text.

    The turn continues without records. The agent answers from the files of the checkout.

  6. 2.6 Dana turns the memory off for one session

    The variable AGENTCORE_MEMORY_DISABLE=1 is the kill switch. Dana puts it before the launch line.

    The extension registers no hook and no tool. This session sends nothing to AWS.

What you learned

  • The core finds the project from AGENTCORE_PROJECT, the Git remote, or the directory.
  • Before each typed prompt, the extension recalls from three namespaces: global, private and the shared namespace of the project.
  • The model reads the records as one hidden context message with a warning line.
  • A slow or failed AWS call costs at most the deadline. The turn continues.
  • AGENTCORE_MEMORY_DISABLE=1 turns the memory off for one session.

What cannot happen

  • Recall cannot read a proposal or a rejected record. The core builds no such query.
  • Dana's agent cannot read /actor/bruno/ or /project/example-site/shared/. IAM denies the request.
  • A prompt cannot change the project of a recall. The project comes from the environment or from the checkout.
  • A denied or failed query cannot stop the turn, and its log line holds no request data.
  • The extension sends no answer, tool output or turn text to AWS. It has no capture hook.

Tutorial 3 · Dana, in Pi

Dana proposes a record

Dana finds a fact that every member of the project needs. She asks the agent to propose it, and she confirms the text before anything is written.

Where: Pi in ~/example-project.

  1. 3.1 Dana asks the agent

    Dana says in plain words what she wants. The agent calls the tool agentcore_propose with a text.

    The tool block shows the name of the tool and its input on one line. Pi shows at most 100 characters of the input and ends a longer input with .... The working line says that the tool waits.

    The agent chooses the words of the text. Dana reads the whole text in the next step.

  2. 3.2 The confirmation dialog

    Pi stops and shows a dialog. Its first line is the target namespace. Its second line is the exact text of the record.

    Dana reads both lines. She presses Enter on Yes. Only then does the core write the record.

  3. 3.3 The record id

    The core writes one record with BatchCreateMemoryRecords. It adds the metadata actorId, projectId, agent, harness, host, session and proposedAt.

    The tool answers with the record id and the namespace.

  4. 3.4 If Dana says No

    Dana can also choose No or press Escape.

    Nothing is written. A Pi session without a dialog, for example pi -p, also answers No.

  5. 3.5 Where the record is now

    Dana's policy allows a read of her own proposals namespace.

    The store answers a list from an index that lags one to five minutes behind a write. Dana waits a few minutes. Then she lists the namespace with her key.

    The record is in /project/example-project/proposals/dana/. Dana and the maintainers of the project can read it. Alice is the maintainer.

    proposedAt is earlier than createdAt. The core sets proposedAt before the dialog, and the store sets createdAt at the write.

  6. 3.6 Where the record is not

    Chen is a member of the same project. He searches Dana's proposals namespace with his own key.

    No other member sees the proposal. Recall never reads a proposals namespace, so no recall shows it, also not a recall of Dana.

What you learned

  • Propose writes one record into /project/<projectId>/proposals/<actorId>/.
  • The dialog shows the target namespace and the exact text. Nothing is written before Yes.
  • The tool answers with the record id.
  • Only Dana and the maintainers of the project can read the proposal.

What cannot happen

  • Dana's agent cannot write to /project/example-project/shared/. IAM denies it.
  • It cannot write to the proposals namespace of another person.
  • A model cannot propose without a human confirmation. A session without a dialog answers No.
  • A proposal is not visible in any recall.
  • A batch with one allowed and one other namespace is denied as a whole.

Tutorial 4 · Alice, maintainer of example-project

Alice reviews as a maintainer

Alice reads the open proposals of example-project. She approves Dana's proposal and rejects a wrong proposal of Chen. Each decision moves the record; nothing is copied or deleted.

Where: Alice's computer, a terminal in her kit checkout ~/tenant-pi. Her person config gives her the role maintainer in example-project and a ledgerPath.

  1. 4.1 Too early: the proposal is missing

    Dana tells Alice the record id of her proposal. Alice shows the proposal at once.

    The store answers a list from an index. The index lags one to five minutes behind a write. show, approve and reject read the list, so they do not find a proposal of the last few minutes.

    Nothing changed in the store. proposal_missing says that the list of Dana's proposals namespace holds no record with this id yet.

    Alice waits a few minutes. Then she lists the proposals.

  2. 4.2 Alice lists the proposals

    The review CLI is part of the core. proposals list --actor lists the one proposals namespace of one member and prints one JSON line per proposal.

    The store reads the namespace of a list as an exact match. A list of the whole tree /project/example-project/proposals/ returns no record. So Alice names each member of the project: Dana, Chen and Bruno.

    Two proposals wait: Dana's and Chen's. Bruno has none. Each line has the record id, the namespace, the author (actorId), the text, the creation time and the metadata.

    The metadata holds the seven keys of propose and the two store keys of text type.

  3. 4.3 Alice shows one proposal

    proposals show prints one proposal. --actor names the proposer and --id the record. The core lists the one namespace of the proposer and finds the record id there.

  4. 4.4 Alice approves with a reason

    Alice names the proposer with --actor dana, as in the show command. The record id alone is not enough.

    The CLI prints a preview with the target namespace and asks on the terminal. No flag skips the question, so an agent cannot answer it through a pipe.

    The reason is optional for approve. It goes into Alice's private ledger only.

    The last line has the same record id. The record moved from /project/example-project/proposals/dana/ to /project/example-project/shared/.

    The move is one BatchUpdateMemoryRecords call with sourceNamespaces and namespaces. The request has no text, so the text stays as it is.

  5. 4.5 The ledger lines of the approve

    The core writes one line before the move and one line after it, in Alice's private ledger. The file has mode 0600 and lies outside every repository.

    approve is the intent. approve-done is the end, with the new metadata approvedBy and approvedAt.

    The intent line holds the metadata as the store gave it, with the store keys. The end line holds the map that the move sends: the seven keys of propose and the two review keys.

    Both lines name the source namespace and the target namespace of the move.

    If the computer stops between the two lines, the ledger shows an intent without an end, and the next move of the record says so.

  6. 4.6 Alice rejects with a reason

    Chen's proposal names port 3000. The shared record says 8080. Alice rejects it. A reject needs a reason.

    The record moved to /project/example-project/rejected/chen/. Recall never reads that namespace. Nothing is deleted.

  7. 4.7 The ledger lines of the reject

    The reject also gets two lines. The reason stays in the ledger and never goes to AWS.

    Chen sees the reason only when Alice tells him.

  8. 4.8 The list is empty

    A few minutes later, Alice lists the proposals of Dana and Chen again.

    No line means no open proposal of that member.

    Right after a move, the list can still show the record in its old namespace for a few minutes. The index lags, as in step 1.

  9. 4.9 The rejected record still exists

    Alice's policy reads the rejected tree of her project. A member's policy does not.

    The AWS CLI lists one exact namespace too, so Alice names the rejected namespace of Chen.

    The record keeps its id and its text. It has one namespace. Its metadata holds the seven keys of propose, rejectedBy, rejectedAt and the store keys.

    Only the owner's admin login can delete it, with the purge of the last tutorial.

  10. 4.10 Chen cannot read his rejected record

    Chen proposed the record. He searches its rejected namespace with his own key. His policy does not name the rejected tree.

    IAM denies the read. Chen's recall does not hold the record either: recall never reads a rejected namespace. The live proof checked both.

What you learned

  • proposals list, show, approve and reject are the four review commands. --actor names the proposer.
  • The store lists one exact namespace. So show, approve and reject need --actor, and list finds nothing without it.
  • The list index lags one to five minutes behind a write. A review right after a propose ends with proposal_missing; run it again a few minutes later.
  • Approve moves the record to the shared namespace of the project. Reject moves it to the rejected namespace of its author. The record id stays.
  • Each move asks on the terminal and writes two ledger lines: the intent and the end.
  • The reason stays in the private ledger. It never goes to AWS.

What cannot happen

  • A member cannot approve or reject. A member holds no BatchUpdateMemoryRecords.
  • A maintainer of example-site cannot move a record into example-project.
  • A maintainer cannot delete a proposal or any other record.
  • A promoted record cannot carry metadata of the maintainer's choice or a key that the proposer added. The core sets the keys.
  • An agent cannot confirm a move of the CLI through a pipe. Without a terminal, the answer is no.
  • Alice cannot list the whole proposals tree of the project in one call. The store answers that list with no record.
  • The author cannot read a rejected record, and no recall holds it.

Tutorial 5 · Dana, in Pi

Dana sees the approved record

The next day Dana starts a new Pi session. The recall now holds her approved record.

Where: Pi in ~/example-project.

  1. 5.1 The next session

    Dana starts Pi with the same launch line and asks about the integration tests.

    The agent uses the approved record in its answer.

  2. 5.2 The record and its metadata

    Dana prints the same block in the terminal.

    The third record line is Dana's record. Its id mem-EXAMPLE4-0000-4000-8000-0000example4 is the id of the proposal.

    Its namespace is now /project/example-project/shared/. Its text did not change.

    actorId still says dana: the author. approvedBy says alice, and approvedAt says when.

    Every member of example-project can now recall it: Alice, Bruno, Chen and Dana.

  3. 5.3 The proposals namespace is empty

    The move took the record out of Dana's proposals namespace. Dana lists the namespace a few minutes after the approve.

    A record has exactly one namespace. Approve made no copy.

    Right after the approve, the list can still show the record for a few minutes. The record itself is already in the shared namespace: the recall of step 2 finds it there.

What you learned

  • An approved record keeps its id and its text.
  • Its metadata names the author, the maintainer and the time of the approve.
  • From now on, every member of the project recalls it.

What cannot happen

  • A record cannot be in the proposals namespace and in the shared namespace at the same time.
  • A person outside example-project cannot recall it. IAM denies that person a read of /project/example-project/shared/.
  • The approved record cannot carry a metadata key that Dana added herself. The core copies only the keys of propose.

Tutorial 6 · Chen, in Claude Code

Chen in Claude Code

Chen uses Claude Code in the same project. The plugin gives Claude the same recall, and the same propose path with the permission dialog of Claude Code as the confirmation.

Where: Chen's checkout ~/example-project. The kit is in ~/tenant-pi.

  1. 6.1 Chen starts Claude Code with the plugin

    The plugin must load in place, because it imports the core of the kit by a relative path. The option --plugin-dir does that.

    Chen ran the two npm ci commands of the plugin README once before.

    Claude Code loads a recall hook and an MCP server with five tools.

  2. 6.2 What the hook returns

    Claude Code runs the hook for each prompt. It gives the hook the prompt, the session id and the working directory on standard input.

    Chen can run the hook by hand. This sends the prompt to AWS, as a real prompt does.

    The hook prints one JSON object. additionalContext holds the same block as in Pi, with Chen's recall set.

    On any failure the hook prints {} and exits with 0, so the prompt goes on without context.

  3. 6.3 Chen asks a question

    Chen types a question in Claude Code.

    Chen has no private record yet, so the block holds no line from /actor/chen/.

  4. 6.4 Chen asks to propose

    The description of the tool memory_propose tells the agent to show the exact text and the target project first, and to ask.

  5. 6.5 The permission dialog

    Claude Code shows its permission dialog with the tool input.

    The tool carries the flag anthropic/requiresUserInteraction. So the dialog comes on every call, also in the modes that skip other dialogs, and an allow rule does not skip it.

    Chen chooses Yes. The server then checks that the core writes exactly the text and the project of the dialog.

  6. 6.6 The record id

    Without a projectId, the server resolves the project from its working directory.

    The record is in /project/example-project/proposals/chen/. Its metadata says claude-code as agent and harness.

  7. 6.7 Chen cannot review

    The plugin also has the four review tools of a maintainer. Chen is a member only. The two read tools follow the normal permission rules of Claude Code.

    The core refuses with the fixed code not_maintainer before any AWS call. IAM would deny the call too.

What you learned

  • The plugin gives Claude Code the same recall and propose as Pi, through one core.
  • The hook prints the context block as additionalContext, or {} on any failure.
  • The permission dialog of Claude Code is the confirmation of a proposal.
  • A tool refusal is one fixed code, for example not_maintainer.

What cannot happen

  • The hook cannot write a record. It calls recall only.
  • A slash command, an empty prompt or a prompt of fewer than three characters sends no query.
  • A failure of AWS cannot block the prompt.
  • An allow rule cannot skip the dialog of memory_propose. The plugin ships no allow entry.
  • Chen cannot list, approve or reject the proposals of example-project.

Tutorial 7 · Dana, in Pi

A directory without a project

Dana works in a directory that is no project of hers. Recall reads only the global namespace and her private namespace. A proposal is refused.

Where: Dana's notes directory ~/notes. It has no Git remote of a project, and her config names no such directory.

  1. 7.1 No project matches

    Dana checks the project of the directory.

    source is none: no variable, no remote and no directory matches.

  2. 7.2 Recall with two namespaces

    Dana starts Pi in ~/notes and asks a question. The core sends two queries: /shared/ and /actor/dana/.

    The block has no project record. The records of example-project stay out of this directory.

  3. 7.3 A proposal is refused

    Dana asks the agent to propose a fact. Without a projectId, the tool resolves the project of the working directory. There is none.

    The refusal comes before the dialog and before any AWS call. The code is project_none.

  4. 7.4 A project of other people is refused

    The model can name a project in the tool input. The core accepts only a project of Dana's config.

    Dana is not a member of example-site. The code is not_member.

  5. 7.5 The override variable

    AGENTCORE_PROJECT names the project for one session. Dana tries example-site in her checkout of example-project.

    A value outside her memberships gives recall without a project. The line comes once per session and holds no value.

What you learned

  • With no project, recall reads only /shared/ and /actor/<actorId>/.
  • A proposal without a project is refused with project_none.
  • A project outside the person's config is refused with not_member.
  • AGENTCORE_PROJECT cannot add a project that the config does not hold.

What cannot happen

  • A prompt cannot change the project of a recall.
  • A model can name a project in a propose call, but only a project of the person, and the write still needs the confirmation.
  • A propose call without a projectId cannot write in a directory outside every configured project.

Tutorial 8 · Alice, the coordinator, and Dana's old key

Dana leaves

Dana leaves the team. Alice removes Dana's access and her private records. Dana's approved record stays. Then Alice purges the rejected records of the project.

Where: Alice's kit checkout ~/tenant-pi and her private registry ~/.config/agentcore-memory-admin/registry.json.

  1. 8.1 Alice runs the dry run

    The offboard command starts as a dry run. Without --profile it reads the registry only and makes no AWS call.

    The plan lists Dana's namespaces in each project of the registry and the order of the apply step.

  2. 8.2 The coordinator lists what goes

    The coordinator is the agent of the owner with the admin login. With --profile, the dry run makes read-only calls: it lists the records and the IAM user.

    Two records go: Dana's private record and one open proposal that nobody reviewed yet.

    Dana's approved record in /project/example-project/shared/ is not in the list. It stays.

    The line list index is a warning. The store answers a list from an index that lags one to five minutes behind a write. A record that a step deleted a minute ago can still be in the list.

  3. 8.3 The apply step after Alice's word

    Alice reads the plan and says yes. The coordinator runs the same command with --apply.

    The access key is deleted before the user, so a copy of the key is useless from now on.

    The registry file now gives Dana the status offboarded, and no project list names her.

    IAM has no user pi-memory-person-dana any more.

    A delete can fail when the list index still lists a record that is gone. The script counts such a delete (error code 404) as done. Any other failed delete stops the step before the IAM steps, and the script prints the code and the message.

  4. 8.4 What Dana's old key gets

    Dana still has the key in her AWS profile. She tries it.

    AWS no longer knows the key. The request fails before any policy is read. The answer is an error and no data.

    The error is UnrecognizedClientException, not AccessDeniedException: AWS does not know the key at all.

  5. 8.5 Dana's recall after the step

    Dana's computer still has her config. She asks the core for a recall, as her agent does before a prompt.

    Each of the three queries fails. The core turns AccessDeniedException into the code aws_denied and every other AWS error into aws_failed. A deleted key gives aws_failed.

    The block is empty, so the command prints no record. In Pi, the same three lines go to the standard error of the Pi process, and the turn continues without records.

  6. 8.6 The approved record stays

    Bruno is a member of example-project. His recall still holds the record that Dana proposed.

    The metadata still names dana as the author. An approved record is project knowledge.

  7. 8.7 The purge: Alice's dry run

    Rejected records stay in the store until the owner purges them. The purge is the one other delete of the owner, beside offboarding and the migration of the old owner namespace.

    The store lists one exact namespace at a time. So the purge lists the rejected namespace of each person of the registry: four namespaces of /project/example-project/rejected/.

    A rejected record of a person outside the registry needs --person with the actorId of that person.

  8. 8.8 The purge: the coordinator lists the namespaces

    The coordinator lists the four namespaces with the admin login. The list makes read-only calls.

    Only Chen's rejected namespace holds a record. The line shows its id, its author, the time of the reject and the first line of its text.

  9. 8.9 The purge: the apply by the coordinator

    Alice reads the list and says yes. The coordinator lists Chen's rejected namespace once more with --person chen, then runs the apply step.

    Chen's rejected record is gone. Alice's ledger still holds its text and the reason.

    Wait five minutes before the next step on the same records. Then a new dry run must list no record of the purge.

What you learned

  • Offboarding is one command: a dry run first, then the apply step by the coordinator with the admin login.
  • The step deletes the private records, the open proposals and the rejected records of the person, then the key, the policy and the user.
  • Approved records stay. Their metadata still names the author.
  • A deleted key gets UnrecognizedClientException and no data. The core turns it into aws_failed.
  • The purge lists one exact rejected namespace for each person of the registry. --person names one namespace.
  • The list index lags. A step right after a delete can still list the deleted record.

What cannot happen

  • Offboarding cannot delete a shared record or remove the author name from it.
  • The last maintainer of a project cannot be offboarded. The owner names another maintainer first.
  • A maintainer cannot purge. The purge needs the admin login.
  • The purge cannot touch /shared/, a project shared namespace, a proposals namespace or a private namespace.
  • The apply step refuses the example registry of the repository and every registry file inside it.

Glossary

Agent
A program that reads a request in plain words and works on files and tools for a person. Pi and Claude Code are agents.
Pi
A terminal agent. The kit generates its profile and loads the extension packages/agentcore-pi.
Claude Code
A terminal agent of Anthropic. It loads the plugin packages/agentcore-claude.
AWS
Amazon Web Services. It runs the memory store and checks each request against the policy of the person.
IAM user
An identity of AWS IAM (Identity and Access Management). Each person has one, named pi-memory-person-<actorId>.
Access key
A pair of an access key id and a secret access key. It proves the IAM user and signs each AWS request.
Inline policy
The rules of one IAM user: the allowed actions and the allowed namespaces. It has no delete action.
Profile
A named section of ~/.aws/credentials that holds one access key, for example pi-memory-person-dana. The person config names it.
Person config
The file ~/.config/agentcore-memory/config.json. It names the memory, the actorId, the profile and the projects. It holds no key.
Record
One fact in the store: a text, one namespace, metadata and a record id such as mem-EXAMPLE4-0000-4000-8000-0000example4.
Store keys
The four metadata keys that the store adds to every record: x-amz-agentcore-memory-recordType, x-amz-agentcore-memory-strategyType, x-amz-agentcore-memory-createdAt and x-amz-agentcore-memory-updatedAt. The first two hold text, so the recall block and the review lines show them. A move does not send them, and the store keeps them.
Namespace
The path of a record, for example /project/example-project/shared/. A record has exactly one namespace.
Actor
One person. The actorId, for example dana, appears in the namespaces and in the metadata of the person.
Project
One shared project with a projectId, for example example-project. The person config maps a Git remote or a directory to it.
Member
A person who reads the shared records of a project and proposes records to it.
Maintainer
A member who reviews the proposals of a project. The owner is the maintainer by default.
Recall
The search before each prompt: one query per namespace of the recall set. The agent reads the result as reference data.
List index
The index from which the store answers a list. It lags one to five minutes behind a write. A review right after a propose ends with proposal_missing, and a list right after a move can still show the old namespace. Wait a few minutes and run the command again.
Proposal
A record in /project/<projectId>/proposals/<actorId>/. Recall never reads it.
Approve
A maintainer moves a proposal to /project/<projectId>/shared/. The record id stays.
Reject
A maintainer moves a proposal to /project/<projectId>/rejected/<actorId>/. Nothing is deleted.
Review ledger
The private file of a maintainer. It gets one JSON line before and one after each approve or reject, with the text and the reason.
Bitwarden Send
A link of the password manager Bitwarden that shares a text or a file for a short time. The Send of a new key opens once and needs a password.
MCP tool
A tool that an MCP server (Model Context Protocol) gives to an agent. The Claude Code plugin has five.
Hook
A program that Claude Code runs on an event. The recall hook runs for each submitted prompt.
Dry run
A run that prints the plan and changes nothing. Every owner command starts with it.
Live proof
The run of the design on the real store with test people, in rounds. The owner gave the word for each write. A frame with a live shape names its round.
Admin login
The administrator session of the owner. It is the only identity that deletes records.
Coordinator
The agent of the owner that runs an apply step with the admin login, after a dry run and the owner's word.
Kill switch
The variable AGENTCORE_MEMORY_DISABLE=1. It stops every AWS call of the extension and the plugin.
